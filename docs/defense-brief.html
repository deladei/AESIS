The system in 60 seconds

If you get one uninterrupted minute, this is what it should contain.

AESIS manages the full lifecycle of a Computer Science internship placement. A student submits a daily and weekly logbook; their assigned academic supervisor reviews each week and either acknowledges it or returns it for revision; the company supervisor contributes a weekly comment, an industry score and a final attestation without ever needing an account, through single-use email links; the coordinator oversees the cohort and releases final grades; and an AI engine reads each entry to produce an advisory quality score, a summary, a plagiarism signal and a chatbot that answers from the department's own regulations.

It is three deployed services in one repository: an Express + Prisma API that is the system of record, a FastAPI service that does all AI work, and a React SPA. It is live in production, not a prototype — the API, the AI engine and the SPA are all deployed and reachable now.

The single design commitment worth stating out loud: the AI is advisory and never grades anyone. Every AI output is clamped, validated and stored on separate tables from the human assessment, and the final grade is composed entirely of human-entered components.

One request, end to end

The most common whiteboard question: “walk me through what happens when a student submits a logbook entry.” Answer it as a pipeline.

  1. 1 · SPA Zod-validated form The same schema file the server uses, mirrored into the frontend, so the client shows the error the server would give.
  2. 2 · HTTP POST /api/v1/entries Bearer access token in memory; refresh token rides as an HttpOnly cookie.
  3. 3 · Guard authenticate → authorize JWT verified, req.user attached, role checked before anything touches the database.
  4. 4 · Policy assertPlacementAccess Ownership decided in one place: is this actor the student, the academic supervisor, or the company supervisor on this placement?
  5. 5 · Machine resolveTransition A pure function decides whether draft → submitted is legal for this role and state. Nothing else may move an entry.
  6. 6 · Write Prisma + entry_event Status change and an append-only event row, backed by a database trigger.
  7. 7 · Enrich FastAPI, fail-open Quality, summary, plagiarism. If the engine is down the entry is still submitted — enrichment status tracks itself separately.
  8. 8 · Notify Socket.io + notification Emitted to the supervisor's own room, user:<id>.

The sentence that ties it together: authorization, state and enrichment are three separate decisions, and they fail independently. A broken AI engine cannot block a submission; an unauthorized actor is rejected before the state machine is ever consulted.

Architecture & stack

Expect “why three services?” and “why this stack and not X?”

Why is the AI a separate service instead of code inside the API?

Three reasons, and the third is the real one. It is a different runtime — the models and the NLP tooling are Python, the API is Node. It has a different failure profile — the engine may be slow or asleep, and the API must answer in milliseconds regardless. And it has a different deployment cadence: the AI engine loads a sentence-transformer at boot and takes 30–60 seconds to start, which would be an unacceptable restart cost for the system of record.

The boundary is an HTTP contract with a shared secret (AI_ENGINE_API_KEY), so the engine can be restarted, scaled or replaced without a migration.

ai/backend/src/shared/utils/aiEngine.ts

Why Prisma rather than raw SQL or another ORM?

The schema is the source of truth and it is large — 51 models across 41 migrations. Prisma gives compile-time types generated from that schema, so a renamed column becomes a TypeScript error rather than a runtime 500. Migrations are versioned files in the repository, and production runs prisma migrate deploy at start-up, so the deployed schema can never silently diverge from the code.

Where Prisma is a poor fit — aggregate reporting — the code drops to raw SQL through Prisma rather than contorting the query builder.

backend/prisma/schema.prisma41 migrations

Why three databases? Isn't that over-engineering?

Be honest here, because it is the fair version. PostgreSQL is the system of record — every relational entity lives there. Redis holds only rate-limiter counters. MongoDB is a legacy document store for logbook entry text and chat transcripts, kept from an earlier design.

The defensible part: Mongo is optional. The code degrades gracefully if it is absent, because nothing that matters academically depends on it. If a panellist calls it unnecessary, agree that a system designed today would use Postgres and JSONB — and point out that the code was written so it can be removed without touching the academic record.

backend/src/config/mongo.tsbackend/src/config/redis.ts

How is the code organised?

Feature modules, not layers. Each feature is backend/src/modules/<feature>/ containing its own service, controller, router and Zod schema, with tests beside it. Twenty-three modules currently. Cross-cutting concerns live in shared/, infrastructure in config/, request guards in middleware/.

The reason to prefer this: a feature is deleted or reviewed in one directory. The logbook consolidation earlier this year removed an entire legacy module without touching another feature's files.

Backend & APIs

The state machine is the strongest thing in this system. Steer questions toward it.

Explain the logbook state machine.

States are draft → submitted → acknowledged, where acknowledged is terminal and locks the week. The revision path is submitted → returned → draft, and a reopen bumps a version counter so a revised week is distinguishable from an original.

Four transitions, each with exactly one permitted role: submit (student), acknowledge and return (academic supervisor), reopen (student). It is implemented as a pure function, resolveTransition(current, action, role), which is why it is exhaustively unit-testable without a database.

The detail worth volunteering: the role guard runs before the from-state guard, so an unauthorized actor gets 403 and never 409. Otherwise the error code itself would leak what state another student's entry is in.

backend/src/modules/entries/entry.stateMachine.ts

How do you know a grade was not tampered with?

Every transition writes an append-only entry_event row, reinforced by a database trigger, so the history exists even if it were written around the application. Assessment and attestation records are immutable once signed off. A coordinator override of an aggregated grade requires a reason, which is stored on the grade and in the audit log — an override is never silent.

modules/grades/grades.schema.tsmodel AuditLog

How is the final grade computed?

Four components, each raw on 0–100: industry, university, report, logbook. Default weights are 30 / 30 / 30 / 10 and are cohort-configurable rather than hard-coded, because the department may reweight between academic years.

The industry component arrives from the company supervisor through a tokenised link; the other three are entered by the assigned academic supervisor. Only the coordinator may aggregate, override or release. Note the deliberate separation: no AI output is a term in this formula.

grades.service.ts · DEFAULT_WEIGHTSgrades.policy.ts

How does a company supervisor participate without an account?

Single-use, hashed magic-link tokens. The token is emailed, stored hash-only, and is consumed on use. There are public router mounts for exactly three flows — attestation, the industry score, and the seven-criterion industry form — and each is scoped to one placement.

The design reason: a company supervisor supervises one student for a few months. Forcing account creation on them is the single most reliable way to get no data at all.

/api/v1/attest/api/v1/grade-invite/api/v1/industry-form

How are the APIs versioned and validated?

Everything is mounted under /api/v1/<resource> — around thirty router mounts. Every request body and route parameter is parsed by a Zod schema before a controller sees it, so a handler never defends against a malformed payload. Responses go through shared helpers (ok / created / noContent) so shape is consistent, and a single error handler converts a thrown AppError into its status code.

backend/src/app.tsmiddleware/errorHandler.ts

What runs on a schedule?

Five background jobs: weekly auto-submit, deadline reminders, a weekly report, an enrichment revival sweep for entries whose AI pass failed, and a keep-warm ping to the AI engine every ten minutes — the last because the engine's hosting plan sleeps after inactivity and a cold start is 30–60 seconds.

Database & data model

Know your own numbers, and know why the schema is shaped the way it is.

Why is a placement, not a user, the centre of the model?

Because every authorization question in the system is really a question about a placement: it carries the student, the academic supervisor, the company supervisor, the company, the dates and the status. Entries, assessments, attestations, grades, documents, visits and messages all hang off it. That is what makes a single policy function — assertPlacementAccess — sufficient for the whole entries pipeline.

model Placementmodules/entries/entries.policy.ts

Why do daily and weekly entries both exist?

They are different academic instruments. DailyEntry records what was done on a given working day, with absences and non-working days modelled explicitly so a gap is never mistaken for a missed obligation. LogbookEntry is the week — the reviewable unit that a supervisor acknowledges and that carries reflection, attachments and objectives.

Conflating them would mean either reviewing every day or losing per-day evidence. This is the SIWES daily-logbook requirement met without breaking the weekly review workflow.

model DailyEntrymodel LogbookEntrymodel Absence

Naming and conventions?

Database columns are snake_case via Prisma's @map; models and fields are camelCase in code. One trap worth stating before they find it: Prisma serialises Decimal as a JSON string, so every numeric value coming out of the database is coerced and validated before arithmetic or rendering — a bug we hit once on a dashboard average and then fixed centrally.

backend/src/shared/utils/quality.ts

Where does production actually run?

Postgres is a free Supabase instance, reached through its session pooler host. It was migrated off Neon after Neon's free tier metered compute-hours and a periodic health check exhausted the quota, which took production down. Mongo is Atlas; Redis is Upstash. All three are external to the application host, so a redeploy never touches data.

Auth & security

This is where a strong panel will push hardest. Answer with mechanisms and lifetimes, not adjectives.

Describe the authentication scheme.

Custom JWT. The access token lives 15 minutes and is held in memory only — never in localStorage, so an XSS payload cannot read it from storage. The refresh token is a 7-day HttpOnly cookie, and is stored in the database SHA-256 hashed, so a database leak does not yield usable sessions. Passwords are bcrypt at 12 rounds. Google sign-in is also live for accounts that prefer it.

The claim set is deliberately minimal — { sub, role } — so nothing sensitive travels in a token the client can decode.

shared/utils/token.tsmodel RefreshToken

How is authorization enforced, and why not row-level security?

Two layers. Route-level RBAC via authorize(...roles), and a per-resource decision point, assertPlacementAccess(actor, placement, mode), where ownership and access mode (read / write / transition) are decided. Controllers never re-implement role rules — that is the property that makes the rules auditable.

On RLS: it was a conscious choice, not an oversight. Authorization here depends on relationships (assigned supervisor, regional assignment, cohort) and on the action being attempted, not just row ownership; expressing that as database policy would split the rules across two languages and two review surfaces. The honest cost is that a raw SQL path that bypassed the service layer would bypass the rules — which is why aggregate SQL is read-only.

middleware/authorize.tsentries.policy.ts

What protects personal data?

Phone numbers and addresses are encrypted at the application layer with AES-256-GCM before storage. GCM specifically, because it is authenticated encryption — a tampered ciphertext fails to decrypt rather than returning plausible garbage.

shared/utils/crypto.ts

Rate limiting and abuse?

A global limiter of 100 requests per 15 minutes per IP, and a tighter 30 per 15 minutes for AI endpoints, because inference is the expensive path. Counters live in Redis so they hold across instances.

The interesting decision is the failure mode: the limiter fails open. If Redis is unreachable the request proceeds unthrottled rather than 500-ing. A cache outage must not take the chatbot down — availability of the academic system outranks perfect throttling.

middleware/rateLimiter.ts

Can someone create an administrator account?

Administrator self-registration is gated on a shared setup code, compared in constant time so a wrong code cannot be discovered character by character from response timing, and it fails closed — if the secret is unset the system refuses admin registration outright rather than leaving the gate open. Coordinator accounts cannot be self-registered at all; they are seeded or invited.

auth.service.ts · assertAdminSetupCode

Does the password-reset endpoint leak which emails are registered?

No, and the defence is in two parts. The response message is identical whether or not the address exists. And — this is the part worth mentioning, because it shows you understood the attack — the email is sent without blocking the response. An awaited send would have made registered addresses measurably slower than unregistered ones, so the response time would have handed back exactly what the wording withholds.

auth.service.ts · resetPasswordInit

The AI engine

The likeliest hostile question of the whole defence is “so is it really AI?”. Answer it directly, and never overclaim.

What exactly does the AI do?

Four things, and they use different techniques deliberately:

1 · Quality scoring — a rule-based rubric over the entry text. The weights are Task Depth 30%, Technical Vocabulary 25%, Reflection 25%, Temporal Consistency 20%. No training data, no model weights, fully explainable: for any score you can say which rubric dimension produced it.

2 · Classification and summarisation — a deterministic keyword classifier with a Groq-hosted LLM producing a feedback draft on top, fail-open.

3 · Plagiarism signal — TF-IDF with a FAISS inner-product index for lexical overlap, plus a MiniLM sentence-embedding stage to catch paraphrase. Stateless: the comparison corpus is supplied per request.

4 · Chatbot — retrieval-augmented generation over the department's own regulations, answered by openai/gpt-oss-120b on Groq.

ai/services/quality_scorer.pyai/services/entry_plagiarism.pyai/routers/enrich.py

Why is the quality score rules-based rather than a trained model?

This is a strength, not a shortcut — say so plainly. There is no labelled corpus of graded Ghanaian CS internship logbooks, so a trained scorer would have been trained on a proxy and would carry unexamined bias into an academic setting. A rubric is auditable by the department that owns the rubric: a supervisor can disagree with a dimension, and the dimension can be reweighted. A neural score would be a number nobody can contest.

Add the boundary: it is advisory. It never becomes a grade component.

How does the chatbot avoid making up regulations?

Retrieval-augmented generation, with the corpus in Postgres, not the filesystem. That distinction has a story behind it, which makes it a good answer: an earlier version read a FAISS index out of /tmp, which the host wipes on every restart — so retrieval was permanently empty and every answer came from the model's priors plus a system prompt while claiming to cite regulations.

Now: passages are chunked by heading, so the natural retrieval unit and the natural citation are the same thing; embeddings are stored alongside the model name that produced them, so changing models invalidates rows instead of silently mixing vector spaces; and retrieval is an exact numpy dot product over normalised vectors, because at handbook scale an approximate index would add a failure mode and buy nothing.

ai/services/knowledge.pymodel KnowledgePassage

What happens when the AI is wrong, or down?

Down is the easy half: enrichment is fail-open and tracked by its own status field (pending → processing → succeeded | failed | abandoned) which never touches the entry's academic status. A submission is never blocked by AI.

Wrong is handled by validation, not trust. Every AI-originated value is validated before it touches the database or the UI — quality scores are clamped to 0–100 and an out-of-range value is logged and rejected rather than stored. AI-suggested tags require human confirmation before they count. And any metric that cannot be computed renders as an em dash, never as zero — a fabricated zero in an academic dashboard is worse than an obvious blank.

ai/services/quality_scorer.py · clamp_quality_scoreshared/utils/quality.ts

Why Groq, and what happens if the model id changes?

Groq's free tier makes inference viable for a departmental pilot with no budget, at roughly 14,400 requests a day — which is why the AI rate limit is 30 per 15 minutes per IP. The model id is environment-set, not hard-coded, and the engine's /health endpoint reports whether the configured id still exists — because hosted providers retire ids, and a silent 404 on a model would otherwise look like the AI simply becoming stupid.

Frontend

Expect questions about state, validation duplication and real-time updates.

How is server state managed?

TanStack Query v5 for anything the server owns — caching, invalidation and refetching are the library's job, not hand-rolled effects. React Context holds only what is genuinely client state: the authenticated user and the access token. There is no Redux, and that is deliberate: nearly all state in this application is server state, and modelling it twice is where staleness bugs come from.

frontend/src/contexts/AuthContext.tsx33 pages · 43 components

Isn't validating on both client and server duplicated logic?

It would be if it were written twice. The Zod schemas live in the backend and are mirrored into the frontend by a sync script, with a drift test that fails the build if the copies diverge. The server re-parses every request regardless; the client copy exists only to put the error next to the field.

The mirroring rather than importing is forced by the deployment: Vercel's build root is frontend/, so a build that reached above it would pass locally and fail in production.

frontend/scripts/sync-shared.mjsshared/validation/auth.ts

How do supervisors see a submission without refreshing?

Socket.io. On connection a client joins a room named for its own user id (user:<id>), and notifications are emitted to that room — so the transport enforces the same per-user boundary the API does, rather than broadcasting and filtering on the client.

backend/src/server.tsshared/utils/socketEmitter.ts

Why React and Vite specifically?

Vite for build speed and native ESM in development; React because the component model matches the domain (a logbook week is a component with a state machine behind it) and because Recharts, shadcn/ui and TanStack Query are mature in that ecosystem. Tailwind keeps styling co-located with markup, which matters when one person maintains 33 pages.

Deployment & testing

“Is it deployed?” is a yes-or-no question with a URL attached. Have the URL.

How does it deploy?

Push to main. Vercel builds the SPA; Render builds the API and the AI engine. The API's start command runs prisma migrate deploy, so schema changes ship with the code that needs them and the deployed schema cannot drift from the application.

Infrastructure is described in render.yaml, and every secret is sync: false — set in the dashboard, never in the repository.

render.yamlVercel root: frontend/

What does CI actually check?

Three parallel jobs on every push: backend (lint, typecheck, migrate a test database, run the Jest suites), AI service (pytest), and frontend (typecheck and a production build). The backend job migrates a real Postgres rather than mocking it, so migration errors are caught before deployment rather than during it.

.github/workflows/ci.yml

How is it tested, and what is tested most heavily?

69 backend test files and 11 Python test modules. The heaviest coverage is exactly where the risk is: the state machine (a pure function, so every state-role-action combination is enumerable), the authorization policy, and the grading spine.

A specific example worth having ready: the AI quality clamp is tested with out-of-range inputs, because the test is not “does the model work” but “can a bad model value reach the database”. That is the difference between testing a feature and testing a boundary.

69 *.test.ts · 11 test_*.py

How do you know production is healthy?

Purpose-built health endpoints, not just a 200. /health/email reports whether mail can actually leave the server, which provider it goes through and what the last failure was; /health/mongo returns 503 when disconnected so a ping fails loudly instead of passing while transcripts go nowhere; the AI engine's /health reports whether its configured model id still exists.

The principle: a health check that only proves the process is running is a health check that lies.

The hard questions

Every one of these is a real limitation. A panel respects a known weakness with a reasoned position far more than a denial — and it removes the possibility of being caught out.

“You have no row-level security. Anyone with the database can read everything.”

Own it

True, and deliberate. Authorization is enforced in the application layer because the rules depend on relationships and on the attempted action, not on row ownership alone. The mitigation is that the rules live in one function per pipeline rather than being scattered through controllers.

Say thisThe trade-off is that a future raw-SQL write path would bypass the rules, so raw SQL is confined to read-only aggregates. If the department deploys this beyond a pilot, RLS on the placement relationships is the first hardening step.

“Password reset tokens are stored in plaintext.”

Own it

Correct, and inconsistent with our own standard — attestation tokens elsewhere in the same codebase are stored hash-only. Anyone with read access to that column could reset an account inside the one-hour expiry window.

Say thisIt is a known defect, it is written down, and the fix is the pattern we already use for the attestation tokens. Do not argue it away.

“Is the quality score really AI, or just word counting?”

Strong ground

It is NLP-based heuristic scoring, and calling it that is the credible answer. The system also contains genuine ML — sentence-transformer embeddings for paraphrase detection and for retrieval — and an LLM for feedback drafting and the chatbot.

Say thisThe rubric is rules-based on purpose: it is explainable and reweightable by the department, and no labelled corpus of graded logbooks exists to train anything better. Choosing an unauditable model for an academic judgement would have been the weaker engineering decision.

“Everything is on free hosting. Is this production-grade?”

Own it

It is a departmental pilot on free infrastructure, and the constraints are real: the AI engine sleeps after inactivity, which is why there is a keep-warm job and a retry on the first chat turn; the database was migrated off one provider after its free tier metered compute-hours and exhausted them.

Say thisThe architecture is not what limits scale — every service is stateless and the data lives in managed stores. Moving to paid instances is a plan change, not a rewrite.

“What stops a student from getting an AI to write their logbook?”

Strong ground

Nothing stops it, and no system can claim to. What AESIS does is make it visible: a plagiarism signal that catches paraphrase as well as copying, a reflection dimension in the rubric that scores first-person analytical language, and a daily entry trail that makes a week fabricated in one sitting look different from one recorded across five days.

Say thisAll of it is advisory evidence for a human supervisor. The system never accuses a student — it surfaces a signal to the person qualified to judge it.

“Why is there a legacy module still in the codebase?”

Own it

The weekly workflow moved from an earlier logbook pipeline to the current entries pipeline. The consolidation was completed in phases and the legacy module was deleted; historical analysis rows are retained because coordinator dashboards report on past cohorts.

Say thisDeleting the code and keeping the data was the deliberate split — the old pipeline is gone, the academic record it produced is not.

“Show me it working right now.”

Prepare

The AI engine may be asleep and takes 30–60 seconds to wake. Warm it before you walk in — open the app and send one chat message ten minutes before the session, and leave the tab open.

Say thisIf it is slow live, name the cause before they ask: free-tier instance, cold start, keep-warm job runs every ten minutes. A known and explained limitation reads as competence; an unexplained pause reads as a broken system.

Demo run-sheet

A demo that follows the academic workflow answers half the questions before they are asked.

  1. Ten minutes before.Open the app and send one chatbot message to wake the AI engine. Leave the tab open. Have a second browser or private window ready for the supervisor account.
  2. Sign in as a student.Show the placement, the day-level progress and the current week.
  3. Fill and submit a week.Say the transition out loud as you click: draft → submitted. Mention that the client is validating with the same schema the server will re-parse.
  4. Switch to the supervisor.The submission is already there — that is the Socket.io room, not a refresh. Show the AI quality score and summary, and state that it is advisory.
  5. Return the week, then reopen it.This is the part panels remember: it proves a state machine exists rather than status strings being written by whoever asks.
  6. Acknowledge the week.Point out that acknowledged is terminal and the week is now locked.
  7. Show the magic-link flow.The company supervisor's attestation or industry score, with no account. Emphasise single-use and hash-only storage.
  8. Show the coordinator view.Cohort oversight, grade aggregation with its four components, and the mandatory reason on an override.
  9. Close on a health endpoint./health/email live in the browser. It demonstrates operational maturity in five seconds and invites a question you can answer well.

Never claim this

Each of these is a claim the system does not support. One overstatement that gets caught costs more than every correct answer gains.

  • Do not say the AI grades students. It scores advisory quality. No AI value is a term in the final grade formula.
  • Do not say the quality scorer is a trained model. It is a weighted rubric. The trained components are the sentence-transformer embeddings and the hosted LLM.
  • Do not say plagiarism detection is conclusive. It is a similarity signal against a supplied corpus, for a human to interpret.
  • Do not say the system is secure. Name mechanisms and lifetimes instead — hashed refresh tokens, 15-minute access tokens, AES-256-GCM, constant-time comparison. Then name the known gaps before they do.
  • Do not invent numbers. If you cannot recall a figure, say which file it is in. Knowing where the answer lives is a better answer than a confident wrong one.
  • Do not describe Mongo as essential. It is a legacy store the system degrades gracefully without.
